# Ledger Database Failover During Storage Maintenance

    **Incident ID:** INC-2025-1007  **Severity:** SEV-1  **Date:** 2025-10-07  **Duration:** 1h 15m
    **Affected systems:** Payments Ledger DB, Transfer Orchestrator, Card Authorisation Service
    **Status:** Closed - post-incident review complete

    ## Summary
    Cloud provider storage maintenance triggered an unplanned failover of the ledger database. Failover succeeded in 20 seconds, but the connection pools in three services kept stale connections to the old primary for up to 12 minutes, causing write failures.

    ## Timeline (UTC)
    - 02:10 Storage maintenance event on primary node
- 02:10 Automatic failover completes in 20s
- 02:11-02:22 Services continue using cached DNS for old primary; writes fail
- 02:25 Services restarted in rolling fashion
- 03:25 Reconciliation confirms no duplicates thanks to idempotency keys

    ## Root cause
    **Stale connections after database failover.** JDBC DNS caching (TTL 600s) and pools without connection validation meant clients did not discover the new primary.

    ## Contributing factors
    - Failover testing was only done against planned, graceful failovers.
- The fix from INC-2025-0419 (idempotency) worked and prevented duplicates.

    ## Customer impact
    Payment authorisations and transfers were delayed or declined for the duration noted above.
    Complaints were handled by the Contact Centre using runbook RB-PAY-004. No funds were lost.

    ## Remediation and action items
    - [DONE] Set JVM DNS TTL to 30s and enable pool connection validation
- [OPEN] Chaos test: unplanned failover quarterly (PLT-802)

    ## Lessons learned
    The incident review board re-emphasised that database failover remains a systemic
    weakness in the payments estate and must be tracked at the quarterly reliability review.
